# MDOCSS Semantic Class Profile 0.1

**Status:** Draft  
**Profile:** `org.mdocss.semantics.core-0.1`

MDOCSS keeps Markdown as the canonical content format and CSS as presentation. Some document roles, however, are not represented by ordinary Markdown syntax. This profile defines a small, application-independent CSS class vocabulary for those roles.

The goal is not to turn Markdown into a new markup language. The goal is to give styles such as APA, MLA, Chicago, organizational reports, accessibility themes, and reading themes stable semantic hooks when the document needs them.

## 1. Principles

1. Use native Markdown/HTML semantics when they already exist.
2. Add MDOCSS classes only for roles that ordinary Markdown cannot identify reliably.
3. A class describes **what content is**, not **how it looks**.
4. Presentation-only artifacts such as margins, page numbers, font choices, running heads, colors, and line spacing do not belong in semantic markup.
5. Semantic markup is optional. A document without MDOCSS semantic classes remains a valid MDOCSS document.
6. Unsupported semantic classes MUST NOT make the underlying content unreadable.

## 2. Namespace

Classes reserved by this profile use the prefix:

```text
mdocss-
```

Applications MUST NOT assign a conflicting meaning to a class defined by this profile.

Authors MAY use unrelated custom classes alongside MDOCSS classes.

Readers SHOULD preserve unknown `mdocss-` classes when round-tripping content.

## 3. Renderer shell

A style-aware renderer SHOULD place rendered document content inside:

```html
<article class="mdocss-document">
  ...
</article>
```

When useful, the canonical body may be wrapped in:

```html
<div class="mdocss-body">
  ...
</div>
```

These wrappers may be generated by the reader and do not need to appear literally in `root.md`.

## 4. Core semantic classes

### 4.1 Document identity and title material

| Class | Meaning |
| --- | --- |
| `mdocss-title-page` | A title-page or document-identification block |
| `mdocss-title` | Primary document title |
| `mdocss-subtitle` | Document subtitle |
| `mdocss-author` | Author or creator display |
| `mdocss-affiliation` | Institutional or organizational affiliation |
| `mdocss-course` | Course, class, or comparable program identifier |
| `mdocss-instructor` | Instructor, supervisor, or comparable recipient role |
| `mdocss-date` | Document date |

### 4.2 Abstract and discovery metadata

| Class | Meaning |
| --- | --- |
| `mdocss-abstract` | Abstract or executive summary block |
| `mdocss-abstract-title` | Explicit abstract heading when required |
| `mdocss-keywords` | Keywords or key terms associated with the document |

### 4.3 References and notes

| Class | Meaning |
| --- | --- |
| `mdocss-references` | Reference, bibliography, or works-cited collection |
| `mdocss-reference` | One bibliographic/reference entry |
| `mdocss-footnotes` | Footnote collection |
| `mdocss-footnote` | One footnote |
| `mdocss-note` | A general source, author, or explanatory note |

### 4.4 Figures and tables

Native HTML elements such as `figure`, `figcaption`, and `table` SHOULD be preferred where available.

The following classes provide stable roles when additional identification is needed:

| Class | Meaning |
| --- | --- |
| `mdocss-figure` | Figure container |
| `mdocss-figure-label` | Figure number or identifier |
| `mdocss-caption` | Figure or table caption/title |
| `mdocss-table` | Table container |
| `mdocss-table-label` | Table number or identifier |
| `mdocss-source-note` | Source or explanatory note attached to a figure/table |

### 4.5 Appendices

| Class | Meaning |
| --- | --- |
| `mdocss-appendices` | Collection of appendices |
| `mdocss-appendix` | One appendix |
| `mdocss-appendix-label` | Appendix identifier |
| `mdocss-appendix-title` | Appendix title |

## 5. What does not need an MDOCSS class

Styles SHOULD use native rendered elements for ordinary Markdown structures:

- `h1` through `h6` for heading levels;
- `p` for paragraphs;
- `blockquote` for block quotations;
- `ul` and `ol` for lists;
- `code` and `pre` for code;
- `em` and `strong` for emphasis;
- `a` for links;
- `table` for normal tables where no special role is needed.

MDOCSS intentionally does **not** define classes such as `mdocss-heading-1` or `mdocss-paragraph`, because those meanings already exist in the rendered document model.

## 6. Authoring

Because CommonMark does not define arbitrary attribute syntax, this profile does not require one proprietary Markdown extension.

Semantic roles MAY enter the rendered document in either of two ways:

1. the author includes standards-based HTML carrying MDOCSS classes inside `root.md`; or
2. an MDOCSS-aware application generates equivalent classes in the rendered document model from structured editing controls or metadata.

Example source using embedded HTML:

```html
<section class="mdocss-title-page">
  <h1 class="mdocss-title">Leadership as Behavior</h1>
  <p class="mdocss-author">Example Author</p>
  <p class="mdocss-affiliation">Example University</p>
  <p class="mdocss-course">BUS 0000</p>
  <p class="mdocss-instructor">Professor Example</p>
  <p class="mdocss-date">October 1, 2026</p>
</section>
```

After the semantic block, ordinary Markdown can continue normally.

Applications MAY offer a friendlier authoring interface while producing the same semantic roles.

## 7. Stylesheet behavior

A stylesheet SHOULD target semantics rather than application-specific DOM structure whenever possible.

For example:

```css
.mdocss-title-page {
  break-after: page;
  text-align: center;
}

.mdocss-reference {
  padding-left: 0.5in;
  text-indent: -0.5in;
}
```

An APA-oriented stylesheet and an MLA-oriented stylesheet may interpret the same semantic roles differently without changing `root.md`.

## 8. Conformance

A **semantic-aware reader**:

- SHOULD generate the `mdocss-document` wrapper;
- MUST preserve authored semantic content when it can safely preserve HTML;
- SHOULD expose the standard classes unchanged to the selected stylesheet.

A **semantic-aware editor** SHOULD preserve recognized and unknown MDOCSS classes unless the user explicitly removes the associated structure.

A stylesheet claiming compatibility with the MDOCSS Core Semantic Profile SHOULD avoid depending on proprietary application classes for its essential layout.

## 9. Extension model

Future semantic roles may be added without invalidating existing documents.

Experimental or application-specific roles SHOULD use a vendor/application prefix after the MDOCSS namespace, for example:

```text
mdocss-acme-review-status
```

The core profile will add classes conservatively. Existing core class meanings will not be redefined within the same major semantic-profile version.
